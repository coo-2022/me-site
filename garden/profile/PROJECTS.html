OpenEarth

2026-07-11 · 5 PR 合入:Knowledge curator agent + reflect 接入无损逐字稿 + Skills 清死代码(main 干净,与 origin 同步)

三条主线,正好对应前面路线图里的「知识库接完」(P1)和 reflect 飞轮主链路打磨:

  • ① Knowledge 域从数据管线补齐到 curator agent(#43+#46):#43 打地基(并行 source 抽取 + extract→raw→compile 三段式管线 + 进度条);#46 是阶段一部署核心——queue + ingest + 进度 + curator agent 闭环:外部 agent 丢文件夹 → 异步 ingest → 文件级队列进度 → AGENTS.md 指针 → agent 自浏览 wiki。curator = daemon(指挥)+ skill 驱动的 agent(引擎),和 reflect 同后端,整套流程由技能定义。两条治理锁:外部 agent 只调 openearth 命令(不碰内部 store)、进度只读队列文件绝不路由给 agent。设计锁定(issue #45):一域一逻辑 agent、skill-over-CLI(非 MCP)、先建 curator 后按 rule-of-three 抽通用框架。
  • ② reflect 打磨(#44→#49):#44 把 reflect 坐实为 in-place 工具型 agent(原地只读 Experience,产出写 scratch,编排器入库,不再搬数据进 workdir);挖出”0 skills”真因 = 权限问题——reflect 继承 analyst 的 localhost 被 cli._analyst 静默路由到无工具的一次性 LLMClient,改默认 reflect→opencode/tools=true 并加 --auto 解开只读门 + store 完整性校验。#49(本会话主体)把无损轨迹逐字稿经 openearth export 接进 reflect 读取路径——修了它在 git store 上一直崩(stitch 缺方法)的预存 bug。
  • ③ Skills 域清死代码 + 飞轮 benchmark(#47):移除遗留 per-trajectory Skills optimizer 阶段及失效 config flag(n_analysts/curate/merge),batch reflect 现为唯一 Skills optimizer 阶段;加 benchmark/Skills/evaluate.py 端到端验证飞轮(baseline 失败→训练合入→训练后成功→ledger 血缘→lineage 标签)。
  • 轨迹格式设计讨论(催生 #49):结论是伪二选一——JSON 做真相源(gate/信用分配/成本核算要精确结构化字段)、Markdown 做派生视图;梳理出轨迹三层视图(真相源 JSON / 完整可读 _render_transcript / 缩略 summarize_trajectory),reflect 该用无损而非有损。关键纠错:outcome 是编排器叠加的不是 agent 产出的(占位 rollout 是 Outcome(0,0),渲染成败要按”是否真打过分”而非按 mode 猜),否则未评分 rollout 被误标失败。
  • 遗留:curator e2e 冒烟收尾(曾被 glm-5.2 分类器瞬时不可用挡住);抽 domain-agent 框架(reflect+curator 已两例);provenance 细化;benchmark 合成落地(Benchmark 域仍空壳)。

2026-07-09 · 公式重算 OOM 事故排查 + reflect-agent 技能自发现机制验证(分支 feat/optimizer-agent)

两条线,都对自演进框架有方法论价值:

  • 方案 B(env 端公式重算)被 OOM 否决,但严格证明了根因。前 156 题跑到 75.0%(117/156,基线 ~52.5%)说明 agent 写的公式大多是对的——只是 openpyxl 从不算公式,grader data_only=True 读到 None 才判错。根因不是轨迹累积/ façade / git store(逐个探针排除),而是 formulas 库对真实 agent 输出的病态工作簿(外部引用 [G:\...xlsx]、公式爆炸)构建巨型依赖图(39815 格、单文件 160s、瞬时 +2.2GB),叠加 glibc allocator 不还 OS → RSS 只升不降 → 攒到 ~13GB 被 kill。结论:方案 B 不可用于批量 eval,转向方案 A(agent 在 Python 里算好值、写字面量)。
  • 方法教训(本会话最值钱的部分):合成复现不可信(合成文件没有真实工作簿的外部引用与公式爆炸);内存问题必须用真实输入逐文件 /proc/self/status VmRSS 打点 + 计时计内存才能定位。中途几个轻率判断(“卡死/轨迹泄漏”)被逐一纠正。
  • 核心验证:reflect-agent 能自己统计失败→自己发现→自己写技能,无需手写。给 reflect.md 加一条“第一步先 cat trajectories/*/fail_reason.txt | ... | uniq -c 做统计发现普遍规律”的指令后,agent 自己 tally 出“90/180 失败(50%)是 got None”、自己连到 openpyxl 不算公式、自己写出 openpyxl-no-formulas.md(质量高于手写版),还顺手修了已有技能里一条有害建议。
  • 关键洞察:信号够(轨迹明文 got None)+ 领域知识共享(我和 agent 都知 openpyxl 不算公式),真正差别是“批量聚合统计”能力——把这项交给 agent 即通用。从“需要 agent 没有的实验能力”降级成“用共享领域知识归纳 agent 自己 tally 的事实”,对任何失败模式通用。
  • 实践参数:批次太大→0 技能(531 目录时 agent 把回合预算耗在逐个探索上来不及下结论);“失败是信号源、成功只是参照”——喂 ~180 fail + 50 succ 就够,别把整批塞进去。

2026-07-08 · reflect-agent 重构 + SpreadsheetBench 规模验证(分支 feat/optimizer-agent,未合 main)

  • 飞轮 4 步变 2 步:优化器从”逐条轨迹→LLM 出文本→外部解析→merge→curate”重构为 batch reflect-agent——一个 agent 看整批轨迹+现有技能库,自己写规整 SKILL.md。外部解析的假技能 bug 从根消失,merge/curate 内生化;gate(无回退门禁)仍是唯一真理源。
  • 规模验证(SpreadsheetBench-Verified 400 题,80 训练/280 held-out 测试,deepseek-v4-flash):训练集 baseline 71.25% → 带技能 72.50%,gate merged;测试集干净重跑 52.50%(147/280)。
  • batch 归纳力验证:80 条轨迹只产出 4 个技能(如 agent 自己统计出”近 40% 失败是 range 边界错误”——单条轨迹看不出的模式),印证 batch 去重有效、playbook 在此规模冗余。
  • 关键经验:agent 会幻觉(编造过不存在的 API),系统正确性靠”gate 只放行真能提升的”,不靠”agent 永远对”;强模型上技能训练集边际收益小(+1.25%),真正价值看泛化。
  • 另修 opencode 三层问题(Ultraworker 插件超时/不稳 provider/超长 prompt 走命令行被静默丢弃,改 stdin)。
