2026-07-14 工作进展总结

主要结论

今天完成并合入了 PR #72：Add pydantic agent backend and Knowledge E2E gating。

核心变化是：OpenEarth 的 Knowledge curator 不再默认依赖 opencode 这类外部重型 agent，而是默认走内置的 pydantic-ai 后端；同时保留 opencode 作为可替换 backend。Knowledge curator 的工作流仍然由 Knowledge 域下的 skill 承载，skill 里保留 shell 命令模板，由 agent 自主读取 skill 并执行。

PR 已合入 main：

  • PR: https://github.com/coo-2022/OpenEarth/pull/72
  • merge commit: e8e91a6708aeeb2964db53770ae01d0239bb322e
  • CI: lint、build、Python 3.10/3.11/3.12/3.13 测试全部通过

完成的功能

1. 统一 AgentBackend 抽象

新增了统一的 agent 执行抽象：

  • AgentRequest
  • AgentResult
  • CapabilityMount
  • OutputContract
  • AgentBackend

DomainAgentRunner 已改为通过 AgentBackend 运行 curator 等内部 agent。这样外部 agent 接入和内部 agent 执行可以走同一类协议，但仍保留角色语义边界：

  • rollout agent：执行任务并产出 trajectory
  • curator agent：处理 Knowledge 摄入、维护和问题发现
  • reflect agent：读 trajectory，写 skill
  • judge agent：评分

2. 内置 pydantic-ai backend

新增 PydanticAIBackend，作为默认 Knowledge curator backend。

它具备：

  • skill_search
  • skill_read
  • read_file
  • write_file
  • bash

关键设计点：

  • 不把 skill 正文直接塞进 prompt。
  • agent 必须通过 skill_search / skill_read 自主发现并读取 skill。
  • shell 能力通过受限 bash 工具提供。
  • 权限由 runtime 控制，而不是写死为 Knowledge 专用函数。

3. 内置 openearth-light backend

新增 OpenEarthLightBackend，作为更轻量的 JSON tool-loop backend。

它和 pydantic-ai 使用同一套工具语义，便于后续替换或降级。

4. pydantic backend 增强 bash 工具能力

今天明确了设计方向：不要把 Knowledge workflow 改成结构化专用函数，例如 knowledge_process_batch(...)；而是让 skill 保持命令模板，agent 通过通用 bash 工具执行。

已实现的安全边界：

  • 默认没有 allow_bash 时禁止 shell。
  • ingest / batch 阶段允许 bash，并允许执行 openearth knowledge-tool ...。
  • maintenance 阶段允许只读 bash，但禁止 openearth knowledge-tool 写入口。
  • 禁止后台命令。
  • 禁止危险命令，例如 rm、git、curl、wget、pip、npm、sudo 等。
  • 允许常见只读或工作区操作命令，例如 ls、cat、find、mkdir、printf、sed、wc 等。
  • 允许常见 shell 组合，例如 &&、||、pipe、2>/dev/null。
  • 校验 openearth knowledge-tool --root，避免误把 Knowledge/ 域目录当成 Experience store root，防止再次出现 Knowledge/Knowledge 嵌套。

5. Knowledge curator skill 保持命令式

确认并修正了以下 skill：

  • kb-compile.md
  • kb-batch-ingest.md

它们继续要求 agent 执行：

  • openearth knowledge-tool extract
  • openearth knowledge-tool save-raw
  • openearth knowledge-tool describe-figures
  • openearth knowledge-tool process-batch
  • openearth knowledge-tool put-page

这样 Knowledge 的抽取、raw/figures 保存、VLM 图片描述、wiki page 编译仍然是 curator agent 通过 skill 驱动，而不是 daemon 或硬编码流程替代 agent。

6. Knowledge benchmark 加强

benchmark/Knowledge/evaluate.py 已加强：

  • 保留流式逐题输出。
  • 在 knowledge-on eval 结束后解析 report。
  • 默认要求 hard >= 1.0，否则 benchmark 失败。
  • 支持 --min-hard 调整阈值。
  • --dry-run 不再要求 report path。

这避免了之前 0/12 但脚本退出码仍为 0 的假阳性。

Knowledge benchmark 仍覆盖：

  1. source ingest
  2. maintain
  3. ask_rewrite_questions
  4. ingest ambiguous/conflict docs
  5. maintain
  6. assert pending questions
  7. knowledge-on QA

过程中发现并修复的问题

1. pydantic 默认没有 bash 工具

最初 pydantic backend 只有结构化函数工具，不足以执行 skill 中的 shell 命令。已改为提供受限 bash 工具，保持 skill 驱动。

2. 不应把 Knowledge workflow 写死成专用工具

曾尝试把 skill 改成 knowledge_process_batch(...) 等结构化工具。这个方向被否定后已撤回，恢复为 shell 命令模板。

3. Knowledge/Knowledge 嵌套风险

之前 agent 可能把 Knowledge/ 域目录当成 store root 传给 knowledge-tool。现在在 bash 工具层校验 --root，如果传入的是 Knowledge domain root 会拒绝。

4. shell 安全检查过严导致 agent 浪费 turn

早期安全规则误判 && 为后台 &，也拒绝 2>/dev/null 和 echo，导致模型不断重试并撞到 max_turns。已修复。

5. maintenance 需要只读 shell

maintenance 虽然不能写 Knowledge store，但 agent 会自然用 ls/find/cat 检查 wiki。现在 maintenance 允许只读 shell，禁止 openearth knowledge-tool。

6. read_file 读目录会让 pydantic agent fatal

已改为返回 observation：目录列表或 path not found，不再抛异常中断 agent。

7. Knowledge benchmark 曾经可能假阳性

之前 openearth eval 即使 0/12，benchmark 也可能退出 0。现在解析 report 并按 --min-hard 断言。

8. capture_output 破坏流式输出

为了读取 report path 曾临时把 eval stdout capture，导致用户看不到逐题流式进度。已改为 Popen 边读边打印，同时保留输出行用于解析 report。

后续建议

  1. Knowledge maintenance 目前会产生重复 pending questions，后续需要做 question 去重或归并。
  2. pydantic-ai backend 的 bash 安全策略可以继续收敛为更明确的 command policy。
  3. 可以补一个 Knowledge benchmark 的 no-knowledge baseline 对比门槛，例如要求 knowledge-on 明显高于 baseline。
  4. Windows 上需要继续验证 service/daemon 安装、shell 工具可用性、PowerShell/cmd 兼容策略。
  5. 后续如接入更多内置轻量 agent，可以直接实现 AgentBackend，不用改 Knowledge curator 编排。
