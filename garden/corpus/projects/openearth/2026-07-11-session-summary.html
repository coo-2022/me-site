一、Knowledge 域:从管线到 curator agent(PR #43 + #46)

阶段一部署的中心是一个 Knowledge curator agent。本日把它从零补齐:

PR #43 — 并行 source 抽取 + compile 管线的地基

  • FileSource:ThreadPoolExecutor 并行文件抽取（--parallel）。
  • registry.run_source:三段式管线 extract → raw → compile，带计时统计。
  • 并行 LLM compile + 批量 git 提交；knowledge compile 文件级进度条。
  • --limit 默认 50 → 0（默认 compile 全部）。

PR #46 — Knowledge curator 本体（阶段一核心，issue #45）

  • queue + ingest + progress + curator agent 闭环：coding agent 丢文件夹 → 异步 ingest → 文件级队列进度（Knowledge/.queue/，运行态、不提交）→ AGENTS.md 指针 → agent 自浏览 Knowledge/wiki/。
  • curator = daemon（指挥）+ skill 驱动的 agent（引擎），和 reflect 同后端（opencode），不是一次性 LLM——整套流程由技能定义。
  • 两条治理规则:外部 agent 只调 openearth 命令（不碰内部 agent/store）；进度只读队列文件，绝不路由给 agent。
  • 附:curator maintain 流程（lint / 待回答问题队列 / 页面提案）、benchmark 套件、Knowledge/.meta/skills/ 下可编辑的 curator 技能、装插件时装 AGENTS.md 指针。

设计锁定（issue #45 讨论）:六域（新增 Tool，暂缓）；一域一逻辑 agent、同后端；skill-over-CLI（非 MCP）；先建 curator，后按”rule of three”抽通用 domain-agent 框架。

二、reflect 打磨(PR #44 → #49)

PR #44 — reflect 坐实为 in-place 工具型 agent

  • reflect 现在原地只读 Experience store（自己用 bash/read 决定读哪些轨迹、读多深、看不看血缘/历史轮），产出写 scratch out/，编排器负责入库。不再把数据搬进 workdir。
  • “0 skills” 谜题真因 = 权限问题，不是反射质量:reflect 因 base_url 继承了 analyst 的 localhost，被 cli._analyst 静默路由到无工具的一次性 LLMClient；改配置默认 reflect→opencode/tools=true，并给 opencode run 加 --auto 解开 external_directory 只读门 + store 完整性校验（读前后 git status 比对）。
  • reflect 思考过程 tee 到主日志（log/reflect/<run>-r<round>.log）。

PR #49 — 把无损轨迹逐字稿接进 reflect（本会话主体产出）

起因是一场设计讨论（见 §四）。落地三处:

  • prompts.py:batch-reflect 提示词新增可用能力 openearth export <id> [--root <store>] -o -（干净逐字稿，子 agent 折叠）/ --json（无损）。不强制——由 agent 自主决定用命令看逐字稿还是直接扫裸 JSON。
  • cli.py(_render_transcript):header 补成 outcome-complete 且 mode 无关——outcome: 行永远打（PASS ✅ / FAIL ❌ / unscored 三态），带打分信号（剔元数据 + bulky patch）、fail_reason、user_feedback、ux_score。关键:区分”打分失败”与”从未打分”——评分是编排器叠加的（打分时往 reward_breakdown 写 phase），故未评分的占位 rollout 渲染成 unscored 而非误报 FAIL。
  • stitch.py:对不追踪子 agent 血缘的 version store 优雅降级（git store 没该功能，那是 SQLite store 的）——修复预存 bug:openearth export 默认（stitched）路径在 git store 上 AttributeError 崩溃。

三、Skills 域清理 + benchmark(PR #47)

  • 删死代码:移除遗留的 per-trajectory Skills optimizer 阶段及失效的 CLI/config flag（n_analysts、curate、merge、老 aggregate 模块）。当前 batch reflect 是唯一的 Skills optimizer 阶段。
  • 加飞轮 benchmark:benchmark/Skills/evaluate.py——离线端到端验证 Skills 飞轮:baseline 失败 → 训练合入 → 训练后成功 → ledger 血缘 → lineage 标签。

四、设计讨论:轨迹该用什么格式(md vs json)——催生 #49

命题:轨迹存 markdown（易读）还是 json（详尽）?

结论:伪二选一——JSON 做真相源，Markdown 做派生视图。 取决于主消费者:

  • xskill 主消费者是 LLM 蒸馏 → 它用归一后的 markdown 当真相源（“三件套” .md/.json/.meta，json 降级为逃生舱）。
  • OpenEarth 主消费者还有 gate / 信用分配 / 成本核算（都要精确结构化字段:tokens/cost/provenance/atoms.offset）→ JSON 必须当真相源，markdown 是派生。

梳理出轨迹的三层视图（本会话关键认知）:

层函数/形态有损?谁用
真相源Trajectory JSON无损gate / query / credit
完整可读视图_render_transcript（经 stitch，openearth export）无损人读 / 调试 / reflect（#49 接入）
缩略视图summarize_trajectory有损（截 24 步 / result 160 字）一次性 LLM prompt

两个纠错（用户实测/指正）:

  1. reflect 该用无损 _render_transcript，不是有损 summarize_trajectory——后者专为塞 prompt 省 token，当轨迹表示会丢信息。
  2. “某些轨迹确实没 outcome”:评分是编排器/gate 叠加上去的，agent 发射的占位轨迹是 Outcome(hard=0, soft=0.0)；inference/ingest 进来的也没评分。故 header 判定不能按 mode 猜 FAIL，要按”是否真打过分（reward_breakdown 有无 phase + 任何真实信号）“，否则未评分 rollout 被误标失败。

md 视图落盘策略:默认 lazy（openearth export 现渲现给，不落盘），主存永远只有 <id>.json；真要 agent ls 就看到，再提供物化到 gitignore 目录的开关。理由:md 是 json 的确定性纯函数、又非真相源，落盘只赚”少调一次 CLI”、赔双倍 git 噪声，不划算。

五、本日关键认知(可复用)

  • 轨迹格式不是二选一:JSON 真相源 + Markdown 派生视图；谁当真相源取决于主消费者的结构化需求（我们比 xskill 重 → JSON）。
  • outcome 是编排器叠加的，不是 agent 产出的:agent.act 返回占位 Outcome(0,0)，env.score 打分后由 _one_rollout/run 回写；渲染成败要按”是否真打过分”，别按 mode 猜。
  • reward_breakdown 是复用筐:混装打分信号（tests/format/judge）、元数据（agent/round/phase）、bulky patch——消费时要挑。
  • 给 agent 的命令必须先自己跑通:接 openearth export 进 reflect 时挖出它在 git store 上一直崩（stitch 缺方法），先修再交付。
  • curator 复用 reflect 骨架:scratch→out→ingest、只读 store、编排器入库——两个域一套模式，为后续抽框架铺路。
