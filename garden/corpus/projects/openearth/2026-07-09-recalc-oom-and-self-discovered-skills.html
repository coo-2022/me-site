2026-07-09 会话纪要：公式重算 OOM 事故 & 技能自发现机制验证

分支：feat/optimizer-agent 一句话：方案 B（env 端公式重算）在 eval 时被 OOM kill；严格证明根因是 formulas 库在病态工作簿上爆内存；转向方案 A（agent 写值不写公式）；并验证了 reflect-agent 能自己统计失败、自己发现、自己写出这个技能——无需手写。

TL;DR

议题结论
方案 B（OE_SPREADSHEET_RECALC=1，env 端用 formulas 库重算）技术可行，但会在 eval 途中 OOM 被杀（156/280 处）
OOM 根因formulas.calculate() 对真实 agent 输出里的病态工作簿（外部引用 [G:\...money-manager-2.xlsx]、公式爆炸）构建巨大依赖图（39815 格），单文件烧 160s CPU、瞬时 +2.2GB；释放后 allocator 不还给 OS → RSS 只升不降 → 攒到 ~10–13GB 被 kill。与轨迹累积、facade、git store、rollout 日志全部无关
方案 B 上限在前 156 个 val 任务上 117/156 = 75.0%（含 recalc），对照无 recalc 基线 ~52.5% → 说明 agent 写的公式大多是对的，方案 A（直接写值）理应能收回这 ~75%
方案 A 的技能从哪来agent 自己产：给 reflect-agent 一条”先统计发现普遍规律”的策略指令后，它自己 tally 出 90/180 失败 (50%) = got None、自己连到 openpyxl 不算公式、自己写出 openpyxl-no-formulas.md（质量高于我打算手写的版本），还顺手修了一条已有技能的有害建议
流式 run_eval已改：每条轨迹完成即落盘 + 抽小分数 + 丢引用。虽然事后证明轨迹根本不是泄漏源（每条 0.1MB，34MB 总量），但修复正确无害，保留

1. 起点：恢复误删技能 + 上方案 B

  • 把上一会话误判为”toxic”删掉的两个技能恢复。
  • 方案 B = 在 spreadsheet/env.py 的 _recalc_formulas(path) 上挂 OE_SPREADSHEET_RECALC=1 开关：env 在 patch 前用 formulas 库把 agent 写进 xlsx 的公式真正算一遍，落盘成缓存值，这样 grader 用 data_only=True 读出来才不是 None。
  • 重跑 spreadsheet eval。

期间网关挂了一次（“刚才网关没有启动”），重启后续跑。

2. OOM 事件与”不要轻易下结论”

eval 跑到 156/280 时被内核杀掉：

Out of memory: Killed process 17607 (openearth) anon-rss:13271528kB

我先后给出过几个错误的早期判断，被用户逐一纠正——这一节的价值在于方法，不是结论：

我的错误判断用户的纠正 / 真相
”卡死了""并没有卡死，只是很慢；不要这么轻易下结论，要证明出具体是怎么漏的"
"轨迹在内存里累积是泄漏”轨迹每条 0.1MB，34MB 总量——根本不是元凶
”formulas 不泄漏”（用一个简单合成文件测的）合成文件不是病态文件；真实 agent 输出才触发；后续 recalc_pathological_probe 反证
”rollout 日志 / git store / facade 哪个在涨”逐一用探针排除，全部无辜

教训：合成复现不可信（合成文件没有真实工作簿的外部引用和公式爆炸）；内存问题要用 /proc/self/status 的 VmRSS 逐任务打点 + 针对真实输入逐文件计时/计内存，才能定位。

3. OOM 根因的严格证明（核心）

3.1 排除轨迹累积

eval_tracemalloc_probe（串行）→ 稳在 ~203MB；eval_parallel_probe（parallel=8，24 任务）→ 稳在 ~183MB。 磁盘上每条轨迹 JSON ≈ 0.1MB，531 条总量 ~34MB。轨迹无关。

3.2 复现爬升

eval_long_probe（80 任务、parallel=8、recalc=1，16GB 机器避免被杀）：

  • 前 73 任务 RSS 平缓；
  • 第 74 任务单步 +2.5GB，峰值 2927MB；
  • 之后继续爬。

→ 不是缓慢累积，是个别任务触发的尖峰。指向”病态工作簿”假设。

3.3 抓到元凶

recalc_pathological_probe：对 eval 残留的真实输出 xlsx（408 个）逐个跑 _recalc_formulas，每文件 20s 超时，记录耗时与 dRSS：

[22/408] t=160.7s dRSS=+2219MB n=39815   BIG
  • 第 22 个文件：单文件重算 160.7 秒、RSS +2.2GB、依赖图 39815 格。
  • 病因：agent 输出里带外部引用（形如 [G:\...\money-manager-2.xlsx]Sheet1!A1）和公式爆炸，formulas 库为它们构建巨型依赖图、全量求值、瞬时分配上 GB。

3.4 为什么”释放了还涨”

formulas.calculate() 算完确实释放（tracemalloc 的 Python 层已归还），但 glibc 的 allocator 默认不把堆顶还给 OS（MALLOC_TRIM_THRESHOLD_ 之下不 trim）。于是：

  • 每遇到一个病态文件，进程 RSS 被顶高一截；
  • 高水位 只升不降（ratchet）；
  • eval 跑几百个文件，RSS 攒到 10–13GB → OOM。

3.5 全部组件的开脱

trajectory store、facade、git store、rollout 日志——逐个用探针测过，内存占用都是常数级。唯一非单调的就是 recalc 路径。

旁证：关掉 OE_SPREADSHEET_RECALC 后，eval 不再 OOM、能跑完。

4. 流式 run_eval（保留，但解的是另一个问题）

openearth/orchestrator/run.py：把”先攒全部轨迹再统一处理”改成每条完成即落盘 + 抽小分数 + 丢引用（_absorb + del traj，ThreadPoolExecutor 里 as_completed 逐个吸收）。

事后证明轨迹根本不是泄漏源，所以这个修复没解决 OOM——但它本身正确、把 eval 峰值内存从”全量轨迹常驻”压到”单条并发量”，无害，保留。

5. 方案 B 上限：测出来是 ~75%

在前 156 个 val 任务上（含 recalc）：117/156 = 75.0%，对照无 recalc 基线 ~52.5%。

含义：agent 写的公式大多数是对的——只是 openpyxl 从不计算它们，grader data_only=True 读到 None 才判错。如果让 agent 改成”在 Python 里算好值、写字面量”，理论可收回这 ~75%。这就是方案 A 的依据。

6. 转向方案 A，以及一个更深的问题

方案 A：教 agent——openpyxl 不算公式；要么在 Python 里算好再 cell.value = 数值，要么直接写字面量。

但真正的设计问题（用户提出）：

什么机制能让 agent 自己总结出这个技能？让它重跑一遍、再审视这些错误？

用户明确否决了两条捷径：

  1. ❌ 我手写这个技能塞进 main；
  2. ❌ 我预先画一个”失败模式直方图”喂给 agent——“画直方图这个太特例了，应该是让它针对失败问题的模式做统计发现普遍规律”。

要的是通用机制：agent 针对自己的失败做统计发现，归纳出普遍规律。

关键洞察：信号 vs 领域知识

  • 信号是够的：轨迹里的 fail_reason.txt 明文写着 mismatch ... expected X, got None（来自 spreadsheet/oracle.py 的判分逻辑）——这是 smoking gun。
  • 领域知识是共享的：我和 agent 都知道 openpyxl 不算公式。所以”我会它不会”不是差别。
  • 真正的差别是：我做了批量聚合 + 实验（tally 全体失败、逐文件计时计内存）；agent 之前只逐条扫、靠”推断”。把”做聚合统计”这个能力交给 agent，就是杠杆。

于是发现从”需要 agent 没有的实验能力”降级成”用共享的领域知识去归纳 agent 自己 tally 出来的统计事实”——对任何环境、任何失败模式都通用。

7. reflect-agent 自发现机制——验证成功

7.1 改动（openearth/services/trainer/textual/skills/reflect.md）

两处：

  1. 把”NO batch statistics as a rule”改成：DO 统计去发现规律；DON’T 把统计当规则写出来。“40% 是 X”是发现信号，不是技能；要把背后的根因转成一条具体的 FACT 或 CODE。
  2. 新增 ## First step: quantify the failure patterns：要求 agent 第一步先用 shell tally trajectories/*/fail_reason.txt，例如 先报数（“N 失败，M 个共 ”），再决定写什么技能。

7.2 验证脚本

  • /tmp/reflect_verify.py：180 失败 + 351 成功 = 531 目录 → 0 技能。
  • /tmp/reflect_diag.py：180 失败 + 50 成功 = 230 目录，并保留 workdir、打印 agent 完整回复 → 2 技能。

7.3 结果：agent 完全靠自己走完全流程

  1. 跑统计：90/180 失败 (50%) 是 'got None'；
  2. 连根因：“agents write formula strings that openpyxl never evaluates; checker reads data_only=True → None”；
  3. 写技能 openpyxl-no-formulas.md（2658B）：
    • 三种失败模式（got None / VALUE! / REF!）；
    • BAD/GOOD 的”先算后赋值”模式；
    • 公式→Python 对照表（SUM / AVERAGE / VLOOKUP / SUMPRODUCT / IFERROR …）；
    • 处理”输入表本身带公式”的情况；
    • 警告 data_only=True 修改再存盘会静默毁公式的陷阱。
  4. 顺手修了已有技能：发现 excel-prototype-first.md 里有一条有害建议（用 data_only=True 加载再改再存），加了 CRITICAL 交叉引用。

质量高于我打算手写的版本。

7.4 一个诚实的实践参数（重要）

批次太大 → 0 技能。531 目录时，agent 把回合预算耗在逐个探索上、来不及下结论写盘。失败是信号源、成功只是参照——喂”全部失败 + 少量成功样本”（~180 fail + 50 succ）就够，别把整批塞进去。这是让机制可靠的关键参数。

8. 结论与遗留项

已确立

  • 方案 B 因 formulas 库 + 病态工作簿会 OOM，不可用于批量 eval（根因已严格证明）。
  • 方案 A 的核心技能 openpyxl-no-formulas 可由 agent 自发现产出，且 reflect 统计发现机制对任何失败模式通用。
  • eval 已流式化（解的是非 OOM 问题，正确无害）。

遗留 / 待决

  1. 技能交付路径（待用户定）：
    • 快：把 agent 写好的 openpyxl-no-formulas.md 加进 main → 跑 280 eval，目标 ~75%（无 recalc、无 OOM）。
    • 正：用新 reflect.md 跑一轮完整训练（rollout → reflect → gate），让技能经 gate 验证后自然 merge 进 main。
  2. train rollout → reflect 的盘上交接重构（task #7）：reflect 不应在内存里直接拿轨迹，要从盘读——架构性修复，非阻塞。
  3. 提交本批改动：run.py 流式化、reflect.md 统计指令、env 开关等尚未提交在 feat/optimizer-agent 上。

可复用的探针（都在 /tmp）

  • recalc_pathological_probe.py — 逐真实文件计时/计内存，抓病态文件。
  • eval_long_probe.py — 80 任务长跑，复现 RSS 爬升与尖峰。
  • eval_tracemalloc_probe.py / eval_parallel_probe.py — 串行/并行排除轨迹累积。
  • reflect_diag.py — 带 workdir 保留 + 完整回复的 reflect 验证。
