大模型推理加速技术调研

整理日期:2026-07-03 ｜ 数据经网络检索核实,文末附引用与证据等级 配套文档:后训练基础设施调研_2026-06.md(RL 的 rollout 生成瓶颈本质就是推理慢,两篇同源)

0. 核心结论

推理加速的本质是打两场仗:一场对”访存”(decode 是 memory-bound,权重和 KV cache 的搬运决定速度),一场对”空转”(GPU 等请求、等 prefill、等长尾)。 2026 年的技术栈已收敛为五层组合拳,生产环境把它们叠着用,总收益可达一个数量级:

层代表技术典型收益
① 调度/批处理continuous batching、chunked prefill吞吐 ~23×(vs 静态批)
② 显存/KV 管理PagedAttention、prefix cache、KV 量化KV 浪费 60–80%→<4%
③ 算法解码投机解码(EAGLE-3)2–6×(无损)
④ 模型压缩FP8/FP4 量化、MLA、蒸馏显存减半再减半
⑤ 系统架构PD 分离、多机并行(EP/TP)各角色独立扩缩

1. 先建物理直觉:推理为什么慢

推理分两阶段,瓶颈完全不同:

阶段干什么瓶颈对应指标
Prefill一次算完整个 prompt,写入 KV cachecompute-bound(并行度高,吃算力)TTFT(首 token 延迟)
Decode一个一个 token 往外吐,每步都要读全部权重+KVmemory-bound(每 token 都要搬运 GB 级数据)TPOT / tokens/s

核心矛盾:decode 每生成 1 个 token,都要把整个模型权重(几十 GB)+ 当前 KV cache 从 HBM 搬进计算单元,算术强度极低,GPU 算力大量闲置。所以推理加速大半是在优化”搬多少字节”,而非”算多少 FLOPs”。 这也解释了后文所有技术的分类逻辑:要么少搬(量化/压缩/复用),要么摊薄(批处理),要么一次搬多干几件事(投机解码)。

2. 第一层:调度与批处理(把 GPU 喂饱)

2.1 Continuous Batching(连续批处理)——地基

  • 静态批要等整批都跑完才换下一批,先完成的槽位空转;连续批处理让新请求随时插入空出的槽位,迭代级调度。
  • 收益:相对朴素静态批 最高 ~23× 吞吐(Anyscale 经典测试口径)。
  • 现状:vLLM/SGLang/TensorRT-LLM 全部标配,已是”默认地基”而非可选项。

2.2 Chunked Prefill(分块预填充)

  • 长 prompt 的 prefill 会独占 GPU 数百 ms,阻塞其他请求的 decode(TPOT 抖动)。
  • 把 prefill 切成小块,和 decode 混合调度,平滑延迟。vLLM 默认开启。

3. 第二层:KV Cache 管理(显存是第二战场)

3.1 PagedAttention(vLLM)

  • 借鉴 OS 虚拟内存分页:KV cache 按固定 block 分配,消灭预留式碎片。
  • 收益:KV 显存浪费从 60–80% 降到 <4%,直接换来并发数/上下文长度。

3.2 RadixAttention(SGLang)

  • 用 radix tree 做跨请求前缀共享,超越平面 prefix cache——多轮对话、few-shot 模板、agent 系统提示词等共享前缀场景,prefill 直接复用,TTFT 显著下降。
  • 这是 SGLang 相对 vLLM 的核心差异点,agent 工作负载(system prompt 长且重复)收益最大。

3.3 KV Cache 量化(2026 热点)

精度收益状态
FP8 KV每 token KV 显存/带宽减半 → 并发或上下文翻倍vLLM 官方博客(2026-04)称已生产可用
NVFP4 KV比 FP8 再减半,上下文/批大小可翻倍,精度损失 <1%(代码/长上下文基准)NVIDIA Blackwell + TensorRT Model Optimizer,最新
INT8/INT4 KV~4× 压缩,精度损失小多方案(SAW-INT4 等)

3.4 架构级 KV 压缩:MLA

  • DeepSeek 的 MLA(多头潜在注意力)把 KV 投影到低秩潜空间,KV 体量比 GQA 低 ~5×(呼应主调研文档 §5.5 的 KV 计算:batch256@131k,GQA-FP8 ~5.1TB vs MLA-FP8 ~1.1TB)。
  • 这是”模型设计阶段就为推理省钱”的代表,2026 年新模型广泛跟进。

4. 第三层:投机解码(算法层免费加速)

原理:小 draft 模型(或轻量 draft head)一次猜 K 个 token,大模型一次前向并行验证——把 K 步串行 decode 的权重搬运合并成 1 次,输出分布与原模型严格一致(无损)。

方案机制收益备注
经典两模型独立小模型打草稿2–3×需维护配对小模型
Medusa目标模型上加多个并行解码头~2×头之间不共享上下文,稳定性一般
EAGLE-3(当前主流)单层 transformer draft head,吃目标模型内部特征接受率 0.80–0.88,2–6×(H100/H200 上典型 3–4×)vLLM/SGLang 已集成;AWS 有并行化变体 P-EAGLE
LongSpec / SpecExtend长上下文投机(兼容 FlashAttention 的 tree attention)长序列 ~100 tok/s解决 >32K 时 draft 接受率下降问题

⚠️ 已知短板:长上下文(>32K)下 draft head 预测变难、接受率下滑;经典 EAGLE 与 FlashAttention 的兼容问题由 LongSpec 类混合树注意力解决。

5. 第四层:模型压缩(量化/蒸馏)

5.1 权重量化路线图(2026 生产建议)

格式场景备注
FP8(W8A8)Hopper/Blackwell 有硬件支持 → 生产首选精度几乎无损
AWQ / GPTQ INT4显存受限(消费卡/边缘)4bit 权重,激活仍 FP16
NVFP4 / MXFP4(W4A4KV4)Blackwell 世代新标准,微缩放 FP4权重+激活+KV 全 4bit,最激进
  • 量化的收益本质:权重字节数减半/减 4× → decode 每步搬运减半/减 4× → tokens/s 近线性提升(memory-bound 阶段量化收益≈压缩比)。
  • 组合拳口径:INT4 量化 + KV 优化 + 连续批处理 + prefix cache,自托管总成本可降 60–80%。

5.2 蒸馏与小模型

  • 大模型蒸馏到小模型(如前沿模型 → 8B/4B),用能力换 10× 速度,路由(大小模型分流)是常见生产架构。

6. 第五层:系统架构(PD 分离与并行)

6.1 Prefill-Decode 分离(PD Disaggregation)

  • 动机:prefill(compute-bound)和 decode(memory-bound)硬件画像相反,混跑互相拖累(prefill 打断 decode → TPOT 抖动;decode 占卡 → TTFT 变长)。
  • 做法:prefill 和 decode 放到不同 GPU 池,KV cache 经高速互联(NVLink/RDMA)传递,两池独立扩缩容。
  • 代表:NVIDIA Dynamo(跨节点协调 TensorRT-LLM/vLLM/SGLang,内建 PD 分离 + KV 感知路由)、DeepSeek 推理架构、Mooncake(KV 中心化,月之暗面)。
  • ⚠️ 冷静观点:arXiv:2506.05508《Beyond the Buzz》指出 PD 分离并非普适赢——KV 传输开销、池间负载不均衡都可能吃掉收益,短序列/小模型场景混跑更优;适合长上下文+大模型+严 SLO。
  • 与 RL 的呼应:这正是你主调研文档里”训推分离”的推理侧镜像——GLM-5 报告同样用 PD 分离做 RL rollout。

6.2 并行策略

并行用途备注
TP(张量并行)单模型切到多卡,降延迟NVLink 域内
EP(专家并行)MoE 模型专家分布到多卡DeepSeek EP64、GLM-5 EP64/DP64;MoE 时代的吞吐关键
PP(流水线并行)超大模型跨节点推理侧较少用
  • MoE 是 2026 主流架构(激活参数 << 总参数),EP + 大批量让 MoE 推理成本远低于同能力 dense 模型——这本身就是”架构级推理加速”。

6.3 注意力算子

  • FlashAttention 系(tiling + online softmax)是 prefill 标配;FlashDecoding 沿 KV 维并行,加速长序列 decode。
  • 已下沉为引擎内置,用户无感。

7. 三大引擎怎么选(2026 生产共识)

引擎定位选它当
vLLM生态最广、模型覆盖最全、免编译默认起点,绝大多数团队
SGLangRadixAttention 前缀共享 + 结构化生成共享前缀重的场景(agent/多轮/模板),TTFT 敏感
TensorRT-LLMNVIDIA 底层极致优化,需编译模型长期固定、要榨干每 token/s 的规模化部署
(跨引擎)Dynamo多节点编排 + PD 分离集群级部署

一句话:从 vLLM 开始;前缀共享收益实测显著再上 SGLang;模型冻结且上量再上 TensorRT-LLM。

8. 与 RL 后训练调研的关系(为什么这篇和那篇是一件事)

推理加速技术在 RL 基建中的角色
连续批处理 + PagedAttentionrollout 生成引擎(verl/AReaL/slime 内嵌 vLLM/SGLang)
投机解码加速 rollout 长尾(部分框架实验中)
KV 量化 + 分层 KV 池主文档 §5.5 内存池的同一问题(partial rollout 的 3–30TB KV)
PD 分离训推分离的推理侧同构;GLM-5 RL 即用
FP8ROLL 等框架的 rollout 用 FP8 推理

RL 的”生成瓶颈占 >70% wall-clock”问题,解法就是本文这套推理加速栈——两份调研在此汇合。
